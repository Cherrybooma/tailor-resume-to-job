# 根据岗位定制简历

根据候选人已经确认的真实经历制作岗位定制简历。优化内容相关性和语言表达，但不得虚构事实。除非用户要求其他格式，否则交付干净、可编辑的 DOCX 文件。

## 不可违反的规则

- 仅将主简历、已确认的个人事实库和用户提供的补充材料作为个人事实来源。
- 不得通过虚构、推断、拔高或拼接事实来产生没有证据的经历、技能、数据、日期、资历、职责、教育背景、论文、证书或成果。
- 区分表达调整与事实变更。可以在不改变含义的前提下改写事实；改变事实含义前必须询问用户。
- 将没有证据支持的 JD 要求标记为能力缺口，不得写入简历或技能清单。
- 不得覆盖主简历或已确认的事实库；始终创建带版本的新输出。
- 将个人数据保存在 Skill 文件夹之外，并存放到用户同意的工作目录。
- 不得在投递版简历中暴露内部事实 ID、可信状态或分析备注。

提取事实或改写简历前，必须阅读 [references/truthfulness-and-evidence.md](references/truthfulness-and-evidence.md)。

## 使用持久化候选人资料库

开始工作前必须阅读 [references/persistent-candidate-vault.md](references/persistent-candidate-vault.md)。

- 首次使用时询问用户是否启用持久化资料库；未经同意不得复制或长期保存个人材料。
- 用户同意后，在 Skill 文件夹之外建立候选人专属资料库，保存 `candidate-profile.json`、`evidence-index.json` 和用户同意保留的证据文件。
- 使用 `scripts/candidate_vault.py` 初始化、登记和校验资料库。不得覆盖原始材料；相同内容按 SHA-256 去重。
- 再次使用时先查找并读取资料库，再处理新 JD。只对新岗位尚缺的事实提问，不要求用户重复上传已经保存且校验通过的材料。
- 新论文、作品、报告、代码或用户回答只做增量更新，并保留来源、事实状态和更新时间。
- 不默认复制超大代码目录或含机密信息的材料；此类来源记录稳定路径或经用户确认后选择性保存。

## 判断工作模式

### 首次使用模式

在不存在已确认事实库时使用。

1. 接收一份主简历。优先使用 DOCX；PDF 或纯文本可用于提取事实。
2. 主动请求与高优先级 JD 要求相关的项目说明、业务案例、论文全文、代码仓库、实验记录、图表、专利、报告、作品集或交付物，而不是只依赖主简历的摘要。
3. 按照 [references/candidate-profile-schema.md](references/candidate-profile-schema.md) 提取 JSON 个人事实库。
4. 在证据记录中保留日期、数据、职位、技术和重要主张的原始表述。
5. 区分已确认、存在歧义、相互冲突和没有证据的事实。
6. 只询问会实质影响当前目标简历的问题，但要主动追问能让核心项目从“项目名称”升级为“问题、方法、验证、结果”的事实。
7. 只有获得用户同意后才保存事实库草稿和证据副本；歧义未解决前，将状态保持为 `draft`。
8. 当现有证据足以定制简历时继续工作，不因非关键字段不完整而停止。

### 再次使用模式

在存在已确认事实库时使用。

1. 定位候选人资料库，校验证据索引，读取已确认事实、草稿事实和本次新增材料。
2. 默认只进行增量更新；除非用户明确纠正，否则保留已确认事实。
3. 为每条新增事实记录来源和确认状态。
4. 仅当高优先级 JD 要求可能得到用户尚未提供的真实经历支持时，提出针对性问题。
5. 使用更新后的证据集定制简历。

如果主简历和旧事实库同时存在，必须核对二者。遇到日期、职位或数据冲突时，不得静默选择更有利的版本。

## 分析岗位 JD

1. 提取 JD 中明确写出的公司、岗位名称、职级、地点、语言和业务领域。
2. 将要求分为岗位职责、必备条件、优先条件、领域知识、资格证书和客观限制。
3. 归一化同义表达，但不得抹去关键差异。例如，可以将 `PyTorch` 归入深度学习工具，但不得把一般 Python 经历当作 PyTorch 经历。
4. 根据 JD 本身给要求排序：
   - `critical`：多次出现、明确标为必备，或属于岗位核心职责。
   - `important`：明显有价值，但并非决定性条件。
   - `optional`：优先、加分或外围条件。
5. 只有候选人证据支持时，才将 JD 中的词语作为 ATS 关键词使用。
6. 选择最接近的岗位类型，并阅读 [references/job-family-guides.md](references/job-family-guides.md)。只有真正的复合岗位才组合多个岗位类型。

## 先补充经历、案例或项目证据再定稿

分析完 JD 后、起草最终简历前，必须阅读 [references/project-evidence-and-writing.md](references/project-evidence-and-writing.md)。

1. 找出最能支撑 `critical` 和 `important` 要求的 2-4 个经历、业务案例、作品或项目。
2. 技术岗位检查问题背景、本人职责、技术方法、实验验证、结果和产出；非技术岗位检查业务情境、目标、本人职责、关键行动、协作对象、交付物和影响。
3. 如果关键维度缺失且会使描述明显单薄，暂停最终定稿，向用户提出一组有针对性的问题，并主动邀请用户上传论文、代码、实验报告、业务报告、作品集、方案、复盘或项目说明。
4. 优先请求原始材料；允许从材料中提取更丰富的真实事实，不要求用户把所有内容手工整理成简历语言。
5. 用户无法补充时，才使用现有证据的窄表述，并明确哪些 JD 匹配仍然缺少证据。

目标岗位属于非技术岗位时，还必须阅读 [references/non-technical-job-guides.md](references/non-technical-job-guides.md)。

## 建立证据匹配表

创建仅供内部使用的匹配表，包含：

- JD 要求
- 优先级
- 支持该要求的个人事实 ID
- 证据强度：`strong`、`partial` 或 `none`
- 建议放入的简历模块
- 可安全使用的关键词
- 能力缺口或待确认说明

按以下规则处理：

- `strong`：重点呈现；如果语义完全一致，可以采用 JD 的术语。
- `partial`：使用更准确、更窄的表达，不得暗示完全掌握。
- `none`：不写入简历，并在能力缺口中说明。

起草前，确认每条拟写入的简历要点至少能追溯到一条有来源的个人事实。

## 制定定制策略

1. 保持候选人的身份、时间线、雇主、学校、资格和事实范围不变。
2. 按照目标岗位相关性调整模块和要点顺序。
3. 为高优先级要求选择证据最强的经历。
4. 先删除或压缩低相关和重复内容，再考虑缩小字号。
5. 每个核心经历、案例或项目使用 2-4 条递进要点。技术岗位覆盖“问题或目标、本人职责、方法或系统、实验验证、结果或产出”；非技术岗位覆盖“业务情境、目标、本人职责、关键行动、协作、交付物、结果或影响”。缺失项先询问，不得用空泛形容词代替。
6. 原材料没有量化的数据就保持不量化。不得编造规模、百分比、延迟、收入、用户数、准确率或节省时间。
7. 优先使用具体名词和动词，不堆砌关键词。
8. 保持简历经得起面试追问，候选人应当能够解释每一句话。
9. 对每项 `critical` JD 要求，确认至少有一条项目或经历要点给出直接或部分证据；不能匹配时明确列为缺口，不得只在技能栏堆关键词。

## 姓名下方的职业定位

- 姓名下方只能写候选人已经具备且有证据支持的专业方向或技术身份，例如“光学系统仿真 | 计算成像 | 光学算法”。
- 不得写目标公司、目标团队、目标产品名称，或候选人尚未获得的职位名称。不得用“某公司目标岗位”暗示候选人已经担任该职位。
- 如果用户希望展示求职意向，可单独使用明确标注的“求职意向”字段；不得把求职意向混入职业身份行。

## 生成 Word 简历

所有 DOCX 创建和编辑都必须使用已安装的 `documents` Skill。处理 Word 文件前，必须阅读 [references/docx-output.md](references/docx-output.md)。

### 先确定模板和照片策略

写入内容前必须阅读 [references/resume-template-and-photo.md](references/resume-template-and-photo.md)，并明确选择模板。不得在没有说明的情况下把带照片的主简历改成无照片版本。

- 主简历中的照片、颜色、字体倾向和信息密度属于候选人的视觉偏好，而不只是装饰。
- 主简历含照片时默认保留照片；只有用户明确要求无照片、投递规范明确禁止，或照片无法可靠提取时才省略。省略时必须在交付说明中说明原因。
- 用户提供专门模板时优先使用该模板；模板只控制视觉与结构，不得引入模板示例中的虚构事实。
- 用户未提供专门模板、但希望版式专业或主简历含照片时，优先使用 `assets/professional-resume-cn.docx`。其中 `[[PHOTO]]` 必须替换为已视觉确认属于候选人的照片，或在无照片版本中彻底移除。
- 只有用户明确要求 ATS 极简版、目标系统禁止照片，或专业模板无法稳定渲染时，才使用 `assets/ats-resume-cn.docx` 或 `assets/ats-resume-en.docx`。

选择一种方式：

- 当源 DOCX 结构稳定且用户希望保留设计时，编辑源 DOCX 的副本。进行最小范围的局部修改并保留样式。
- 当源文件依赖不稳定文本框或浮动元素、但候选人希望保留照片和较好的视觉表现时，使用 `assets/professional-resume-cn.docx` 重建。
- 当输入为 PDF 或纯文本、用户没有提供可编辑模板，或者用户明确要求 ATS 优先的新版式时，使用 `assets/ats-resume-cn.docx` 或 `assets/ats-resume-en.docx`。
- 只有用户明确要求新设计，或者上述两种方式都不适用时，才创建全新设计。

对于学生、应届生和工作经验较少的候选人，默认输出恰好一页；除非用户明确要求两页，或现有高价值证据确实无法在一页内清晰呈现。页面既不能溢出，也不能留下明显空洞：最后一个有效模块应自然结束在页面底部安全边距之上，整体视觉填充约为可用正文区域的 90%-98%。

当内容不足一页时，依次：补充核心项目证据并扩展真实的技术链路与验证结果；加入相关论文、专利、课程、奖项或工程细节；微调模块顺序、段前段后、行距与字号。不得通过空话、重复内容或夸张留白填满页面。

当内容超过一页时，依次：删除低相关内容；合并重复要点；压缩措辞；再微调间距、边距和字号。正文不得小于 9.5 磅；若仍无法清晰容纳，先向用户说明取舍或请求允许两页。

每次进行有实质影响的 DOCX 修改后：

1. 使用工作区提供的 Python 运行环境和 `python-docx` 创建或编辑 DOCX。
2. 只有 `python-docx` 无法支持所需功能时才使用 OOXML。
3. 使用 `documents` Skill 的 `render_docx.py` 将 DOCX 渲染为逐页 PNG。
4. 以 100% 缩放检查每一页。
5. 修复文字裁切、内容溢出、不自然分页、缺字、字体替换、对齐偏移和过多留白。
6. 每次修改版式后重新渲染。
7. 只有最近一次渲染通过后才交付。若渲染环境不可用，明确说明未完成的检查。

将投递版命名为 `<候选人>_<公司>_<岗位>_<YYYYMMDD>.docx`。删除批注、修订记录、占位文字、内部备注、隐藏数据和工具标记。不得覆盖已有版本。

## 返回结果

交付：

1. 一份适合直接投递、干净且可编辑的 DOCX。
2. 一段简洁的聊天说明，包含：
   - 证据最充分的岗位匹配点；
   - 主要内容和顺序调整；
   - 没有支持或只有部分支持的 JD 要求；
   - 仍需候选人确认的主张。
   - 本次新增或更新到候选人资料库的事实和材料；如果未启用持久化，明确说明下次可能需要重新提供来源。

只有用户要求时才创建带修订的审阅版 DOCX 或 PDF。投递版不得包含批注和修订记录。

## 最终质量检查

确认以下各项：

- 每项个人主张都能追溯到用户提供的证据。
- 没有将无证据的 JD 关键词写成候选人经历。
- 日期、职位、学校、雇主和数据保持一致。
- 高优先级 JD 要求获得与其重要程度相符的强调。
- 每个核心经历、案例或项目均形成适合岗位类型的证据链，而不是只有工具、职责名词或空泛形容词。
- 姓名下方没有目标公司、目标团队或未获得的职位名称。
- 简历简洁、易读，并能经得起面试追问。
- 联系方式准确，文件名没有意外泄露不必要的个人信息。
- 已选择与用户偏好一致的模板；如果主简历含照片，照片已保留或已明确说明省略原因。
- 最终 DOCX 可以编辑，且每一页都通过视觉检查。
- 对默认一页简历，页面没有溢出，也没有明显大块空白，正文自然填充到接近底部安全边距。
- 主简历和事实库原件均未被修改。
- 资料库已增量更新且证据索引可校验；未复制用户未同意长期保存的材料。
